## The problem it solves

The most common way an AI analyst goes wrong is not bad arithmetic. It is the right arithmetic on the wrong thing: gross sales instead of net, refunds counted as revenue, the neighbouring column, the wrong month. The answer looks confident and is quietly about something else.

So the engine never computes "revenue" from a question. It first writes a **metric definition**: which table, which column, which rows are left out, which date. You can read it in one sentence, and every number in the report is computed from it.

**Validation.** Before it is accepted, code checks every part against the profiled table: the column exists and holds numbers, the filters name real columns, the time column is a date. A definition that fails is refused with a reason, so a model that invents a column name gets nowhere.

## The ideas behind it

### A semantic layer

Analysts call this a *semantic layer* or *metric layer*: the meaning of each business number is written once, in one place, and every query uses it. It is why the engine can say "revenue fell" and you can check what "revenue" meant.

### The model drafts, code decides

When a model is configured, it drafts the definitions from the column names and profile, because naming things is what language models are good at. The output is [structured](../../glossary/#structured-output): YAML that must parse and pass validation. With no model, deterministic rules draft the same kind of definitions (that is what happened in the [tutorial](../../tutorials/confirm-metrics/)). Either way, a person can confirm, edit or drop each one.

### Parameterised SQL

Values such as `'refunded'` travel as parameters (`$1`), not as text glued into the query. That rules out SQL injection from a cell value, and it means the verifier can re-run the exact query later.
