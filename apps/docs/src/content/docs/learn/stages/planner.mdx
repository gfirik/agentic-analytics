**Stage 6 of 10.** `EXPLAIN` investigates each top finding; `DECIDE` proposes actions. This is where a language model works, as the **planner**.

## The problem it solves

The analysis found *that* revenue fell and *where*. Turning that into an explanation means deciding what to look at next: drill into customers? search the documents? compare with a benchmark? That is judgement, and judgement is what language models are useful for. But a model left free will write numbers from memory, run whatever code it likes, and present guesses as causes.

So the planner is given a job, a budget and a short list of fixed tools, and its answer must fit a schema. It never sees raw document text and never writes a number.

Notice what came back: `search_documents` returned **extracts** (typed records with quotes), not the documents. `drill_down` returned **facts with IDs**, computed by SQL. `search_web` returned the query that was actually sent. `compare_benchmark` returned the gap as a fact. The planner can combine these; it cannot invent them.

**Then it writes, in a schema.** After investigating, the planner answers with a JSON object that must match a schema (<code>{g.structured?.schema}</code>): a title, explanations with the extracts they rest on and a [causal grade](../../glossary/#causal-grade), alternatives it rejected, and a confidence. ## The ideas behind it

### Tool calling

[Tool calling](../../glossary/#tool-calling) lets a model ask for an action instead of writing an answer: it emits a tool name and arguments, the engine runs the tool, and the result goes back to the model. The set of tools is the model's whole world here. There is no `eval`, no generated code, no shell. A budget caps the calls per finding and per job.

### Structured output

[Structured output](../../glossary/#structured-output) means the model's answer must parse as JSON matching a schema. When it doesn't, the error is fed back and the model tries again (twice at most). Endpoints that can enforce a schema natively do; for the rest, the engine validates with the same schema.

### Placeholders instead of numbers

A model that writes “revenue fell {factText(learn.analysis.change.pct).replace("−", "")}” may be right or may have made the number up; you can't tell from the text. So the planner writes <code>{`{{${learn.analysis.change.pct}}}`}</code> and code fills in the stored value. A placeholder pointing at a fact that doesn't exist is caught at once.

### Small-model mode

Small local models struggle with long tool loops. `--small-model` halves the budgets and replaces the free-form loop with a fill-in form. The numbers are the same either way, because the model computes none of them. The DECIDE request also stays under a 6,500-token input budget, trimmed in a fixed order that never changes a number ([Running free](../../../models/running-free/)).

## Try it

With a model configured, run a job and watch the stages (`--log` adds structured logs on stderr):

```bash title="Terminal"
bun run aa analyze examples/coffee-roaster --yes --currency USD --today 2026-07-01 --log
```

Without one, the scripted planner replays this page's run: [Analyse your first file](../../tutorials/first-file/). To run a real free model, see [Model router & free providers](../models/).
