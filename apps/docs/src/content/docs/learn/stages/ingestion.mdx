**Stage 1 of 10.** The first two stages, `INGEST` and `PROFILE`, read your files and measure them. No language model runs here: everything is code and SQL.

## The problem it solves

A business spreadsheet is not a database table. The coffee roaster's workbook has a title-less `Orders` sheet, and a `Monthly` sheet the owner keeps by hand, with *two* tables side by side on it. Dates like `03/04/2026` could mean March 4th or April 3rd. One cell is a thousand times too big. If you paste a sheet like this into a chatbot as text, it has to guess where the tables are and what the columns mean, and it guesses silently.

So before anything is analysed, the engine turns each file into something it can query exactly, and writes down every problem it finds as a **data-quality item** that the report shows you.

**Tables, not text.** The workbook is read as a grid of cells. The engine looks for rectangular blocks with a header row, so it found {learn.ingest.tables.length} tables in one file: <code>{orders.sheet}!{orders.range}</code> with {count(orders.rows)} rows, and two tables on the `Monthly` sheet ({learn.ingest.tables.slice(1).map((t) => `${t.sheet}!${t.range}`).join(" and ")}). Each table is loaded into [DuckDB](../../glossary/#duckdb), an embedded SQL database that lives in one file per job.

**Columns get types.** The <code>{orders.sheet}</code> table's columns were typed as: {orders.columns.map((c) => `${c.name} (${c.type})`).join(", ")}. A type is what lets SQL add up `amount` and group by `channel`.

**Documents become sections.** The PDF is split by page, the Word file by heading, the email keeps its headers. That gave {learn.ingest.sections.length} sections, each with its position, so a quote can later point at exactly where it came from. The text is stored but not read by any model yet.

**Profiling finds the mess.** The profiler measured every column in SQL and raised {q.length} data-quality items:

## The ideas behind it

### Structure before meaning

A language model reads a spreadsheet pasted as text one token at a time. It has no reliable way to tell a header from a total row, or one table from the next. Detecting regions in the grid is ordinary code, and it is either right or visibly wrong. The rest of the pipeline relies on that: a number in the report is a SQL query over a known table and known rows.

### Profiling

[Profiling](../../glossary/#profiling) means measuring the data before trusting it: counting nulls and distinct values, finding the date range and the grain (day, month), looking for duplicate keys, and flagging values far from the rest. The ×1000 cell above is caught with a robust rule: a value about 1,000 times the column's median is almost always a unit or decimal-point slip, not a real cost.

### Ambiguous dates

`03/04/2026` fits both day-first and month-first. The profiler counts the values that fit only one order (a day above 12 settles it) and reads the whole column that way, then reports how many dates were ambiguous. It never guesses quietly.

## Try it

`aa metrics` runs ingestion and profiling on your files and stops before any analysis. It needs no model:

```bash title="Terminal"
bun run aa metrics examples/coffee-roaster --yes --currency USD --today 2026-07-01
```

The [first tutorial](../../tutorials/first-file/) runs the whole job.
