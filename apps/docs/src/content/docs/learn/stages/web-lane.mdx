## The problem it solves

Some questions need the outside world: is a refund rate of <Fact id={refundRate} /> high for a coffee roaster? But a search query is a message to a third party. A careless query that names a customer, or carries a number from your books, tells a search engine who your customers are and how much they buy. And a web page is text written by a stranger, which may contain instructions aimed at AI systems.

So the lane cleans every query before it leaves the machine, refuses to fetch addresses that point inside your network, and treats every page as untrusted.

## The ideas behind it

### Data minimisation

Send the least that answers the question. The sanitizer normalises before matching (case, accents, look-alike digits, legal forms like “LLC”), so “HOTEL GROUP llc” and “Hotel-Group” are caught too. When in doubt, a term is removed.

### SSRF

Server-side request forgery is tricking a server into fetching an address *you* choose, usually one only the server can reach: a database admin page, `localhost`, a cloud metadata service. The fetcher allows only http(s) on ports 80 and 443, checks every address the name resolves to at connect time (so a name that later points inside can't slip through), and re-checks each redirect.

### Indirect prompt injection

A model that reads web pages can be steered by the pages. The defence here is architectural: pages are screened, and only the quarantined extractor, which has no tools, reads them. See [Security](../security/).

## Try it

The web lane needs a search engine; the project ships a self-hosted SearXNG:

```bash title="Terminal"
docker compose --profile web up -d searxng
bun run aa run examples/coffee-roaster --web --embedder hash --today 2026-07-01 --currency USD
```

That needs a configured model for the planner. The offline record above comes from the test fixture the CI uses.
