# M4 plan: Metric layer

Branch: `m4/metric-layer`. Human gate: `no`.
Sources: docs/ROADMAP.md M4, docs/specs/metric-layer.md (all sections), docs/specs/security.md §2–3 (untrusted cell text), docs/specs/models.md (extractor role, FakeModel), report-schema `ReportMetric`.

## Pipeline

profile summary (M3) → **digest** (tables, columns, types, ≤ 5 masked samples) → **draft**: the extractor model proposes metric YAML, or the deterministic fallback runs when there is no model or the model fails → **validate** in code (every proposal accepted or rejected with reasons) → **review** (CLI: accept / edit / drop; `--yes` keeps everything as `assumed`) → **compile** each metric to parameterized SQL → `metric_defs` rows → values per period.

## Tasks (in order)

1. **Expression and filter language.** Tokenizer and parser for metric `expression` and `filters`. The result is a typed AST; strings never reach SQL as text.
   - Expressions: column refs, numbers, `+ - * /`, parentheses, unary minus, `abs()`, `coalesce()`. In `derived` metrics, refs are metric ids.
   - Filters: comparisons (`= <> != < <= > >=`), `IN (…)`, `IS [NOT] NULL`, `AND`/`OR`/`NOT`, parentheses. Literals are quoted strings, numbers and booleans.
   - The AST compiles to SQL with checked identifiers, and every literal becomes a `$n` parameter.
2. **Validation (spec §2.3).** Every proposal is checked, and each failure gets a stated reason:
   - id: snake_case and unique;
   - table and every column exist;
   - types fit the aggregation (sum and avg need numeric columns);
   - filters and expressions parse, and their columns exist;
   - dimensions exist and are categorical;
   - the time column is a date;
   - ratio terms are valid, and the denominator gets an automatic `NULLIF(…, 0)` guard;
   - derived metrics only reference known metrics, with no cycles;
   - the unit matches the column types;
   - the currency is present for currency units, using the job's default currency or `XXX` (ISO "no currency") as an assumption.
3. **Compiler (spec §4):**
   - `compileMetric(def, { from, to, grain, groupBy?, where? })` produces `Sql` returning `period, [group cols…], value`.
   - Supported types: sum, count, count_distinct, avg, ratio (one CTE per term, joined on period and groups, ×100 when the unit is percent) and derived.
   - Periods are computed from the metric's time column at the job grain (`strftime`, ISO week `%G-W%V`, quarter).
   - `runMetric(ws, …)` executes it.
4. **Digest (spec §2.1):**
   - only tables, columns and types, plus ≤ 5 sample values per column;
   - values that look like a person's name or a contact (emails, phones, entity columns) are masked;
   - samples sit inside data delimiters; the prompt states they are data, not instructions (security §3).
5. **Drafting (spec §2.2):** the extractor role uses `generateObject` with the proposal schema and a library of common business metrics (from spec §2.2), and validates the result.
6. **Deterministic fallback (spec §2.4):**
   - money-named currency columns become `revenue` candidates;
   - refund or return status values give `refund_rate`;
   - an id column gives `orders`;
   - a two-value channel-like category gives per-member revenue (e.g. `wholesale_revenue`).
7. **Plain language and review (spec §3):**
   - `describeMetric(def)` gives "Revenue = sum of amount where status is not refunded, per month, in USD".
   - `reviewMetrics(drafts, io)` with injected IO: accept / edit (YAML) / drop; `--yes` makes everything `assumed`.
   - Confirmed or assumed definitions are written to `metric_defs` and optionally saved to and loaded from `agentic-analytics.metrics.yaml` for reuse.
8. **CLI:** `aa metrics <paths…> [--yes] [--save file] [--metrics file] [--currency CODE] [--today …]` runs ingest → profile → draft → validate → review. It prints each metric in plain words, its compiled SQL, and its values for the last periods.
9. Ledger, READMEs.

## Acceptance → proof

| Criterion | Proof |
|---|---|
| `revenue`, `wholesale_revenue`, `refund_rate` drafted correctly with FakeModel | test: FakeModel scripted with a proposal → validated → compiled → values per month equal answers.yaml (revenue 41,200 … 37,000; wholesale 14,800 … 7,300; refund rate 1.1 … 3.4) |
| …and with a real free model | DEFERRED (no model configured): `bun run aa metrics evals/datasets/coffee-roaster-v1/files --yes` with `PLANNER/EXTRACTOR_MODEL` set |
| Invalid proposals rejected with reasons | test: unknown table/column, sum over text, unparseable filter, injection attempt in an expression, ratio without denominator, derived cycle → each rejected with its reason |
| Compiled SQL matches hand-computed values | per-type tests on a small table with hand-computed answers in comments; coffee-roaster monthly values |
| Confirm flow in the CLI | test: `reviewMetrics` with scripted IO (accept / edit / drop); `aa metrics … --yes` demo |

## Risks

- The model may propose SQL-ish expressions outside the grammar. They are rejected with a reason, and the fallback still provides `revenue`.
- Percent conventions: profile stores fractions, while report facts use percentage points. The compiler multiplies by 100 only for percent-unit ratio and avg metrics, and tests pin it down.
