# Plan: M14 Measurement foundation

**Source:** docs/plans/analyst-grade.md §4 (accuracy program) and §5 "M14". Built under the autonomy rule (STATE, 2026-10-21): where the plan says the maintainer reviews or decides something, the agent does it and records the choice in STATE.

**Goal:** every later milestone shows its effect in numbers. M14 builds the measuring tools and publishes today's engine on them, gaps included.

## Specs

One new spec, **docs/specs/accuracy.md**, holds the golden-set format and scoring, the bootstrap, `--repeat`, the ablation arms and measures, the held-out sets and the matrix runner. Each PR adds its section to it with the code. docs/EVALS.md links to it, and its line 37 ("The golden set (hand-reviewed) is 10 of them", meaning 10 synthetic datasets) is renamed "the reviewed synthetic subset", so "golden set" means only the M14 question set.

## PRs, in order

1. **Golden-set format, scorer and bootstrap** (`evals/golden/`).
   - A Zod schema per item: question, kind (numeric, categorical or trap), expected answer, tolerance, the SQL that computes it, `split` (dev or held-out), and the review record (see "Golden-set review" below).
   - The scorer:
     - each item names its answer source, either the facts the `aa ask` answer cites or a report section with its metric, period and member. Only that fact is compared, so a matching but unrelated fact scores nothing (tested);
     - numeric answers match within tolerance, categorical answers exactly;
     - traps pass only on a structured refusal (an answer with no verified claim; a caveat beside claims is not one, accuracy.md §2): the engine's `notCovered` (ask) or a caveat field, and the arms' `refused` / `caveat` fields in their fixed JSON shape. Free text is never judged.
     - A question the scripted baseline can't map to a report section and doesn't answer through `aa ask` scores as a miss, not n/a.
   - The paired bootstrap as a pure function (10,000 resamples, fixed seed, 95% interval).
   - Hand-computed tests for both.
   - **CI path:** a committed mini golden set over the committed coffee-roaster dataset (about 6 items, traps included), scored against a FakeModel run.
2. **The matrix runner** (`aa eval --models <list>` or a config list): runs one suite across several model routes and writes per-model results. It comes before the repeat and ablation runs, which use it.
   - **CI path:** two FakeModel "models" on the smoke suite, results checked per model.
3. **Golden sets for the existing real datasets** (Online Retail II, NZ card spend).
   - About 10 items each, about 20% traps; items written by one session, the review by another (see below).
   - **CI path:** the real data isn't committed, so the real-data golden tests are skipped when the derived files are absent. The local command is recorded (`bun run eval:real:fetch && bun run eval:golden`). The scorer is already covered in CI by PR 1's mini-set.
4. **Two new real datasets** (§4.1a first wave): hotel bookings (the *Data in Brief* supplement, CC BY 4.0) and EIA-861M (public domain).
   - Fetch scripts like `evals/real`: the licence text is re-checked on every download, and checksums are pinned.
   - Real-tier answer files, and about 10 golden items each.
   - **CI path:** as in PR 3.
   - If a publisher's host blocks this machine (ScienceDirect often does), the fetch script and answers still ship, and the run is DEFERRED with its command. Golden v1 then has three datasets until it runs, and the baseline says so.
5. **`aa eval --repeat N`:** consistency over N runs.
   - The eval always builds a file cache today (apps/cli/src/main.ts). This PR adds `--no-cache`, with no reads and no writes, so runs 2–5 can't hit run 1's entries. A test shows the call records are `cached: false` across repeats.
   - The five agreement measures of §4.3.
   - Disagreements are written side by side.
   - **CI path:** FakeModel with a scripted variation, so the agreement measures are tested on known disagreements.
6. **Ablation arms A and B** (`evals/ablation/`, with the prompts and harness published).
   - **Arm A:** the files as text, cut to the model's context window minus the prompt, by whole rows, with the cut stated in the input. Online Retail II's about 1M rows mean arm A sees a sample there; the results say so beside its numbers.
   - **Arm B:** a DuckDB of the same tables and one `run_sql` tool, with no metric layer and no verifier.
   - **Same for all arms:** the same tasks, model and scoring, and the same retry budget: 2 retries on invalid JSON or a tool error. Arms A and B get a strong system prompt (the task, the fixed JSON answer shape, "use only the data given, refuse when it can't answer"), published with the harness. A model that can't call tools runs arm A only.
   - **Containment.** Arms A and B are eval-only controls (analyst-grade §4.5, §6.4), not the agent, and they break two rules on purpose: arm B runs model-written SQL (§2.6) and arm A feeds raw untrusted text to a model (§2.5). So they are fenced in:
     - arm B's DuckDB is built for each run in two phases: a writable instance loads the ingested source tables only (no metric definitions, facts or document chunks from the engine's workspace; a test lists its tables) and is closed, then the file is reopened locked. The per-run database and temp directory are deleted after the run (AGENTS §9);
     - the locked open is `DuckDBInstance.create(path, { temp_directory: <per-run dir>, max_temp_directory_size: "1GB", access_mode: "READ_ONLY", enable_external_access: "false", autoinstall_known_extensions: "false", autoload_known_extensions: "false", memory_limit: "1GB", threads: "2", lock_configuration: "true" })`. Order matters, and was checked on @duckdb/node-api 1.5.6: `temp_directory` comes before `enable_external_access=false` (after it, the open fails with "Failed to set config"), and `lock_configuration` comes last. A test reads back `current_setting` for all nine options and compares normalised values (`memory_limit` reads back as "953.6 MiB", so bytes are parsed; booleans and `access_mode` case-folded), so dropping one fails CI. This bounds RAM, threads and spill (AGENTS §9), as well as files and the network; (as built, PR 6: `max_temp_directory_size` passed to `create` is read back but not enforced on 1.5.6, so `create` takes the first eight options and the cap and the lock are then applied with `SET`, the lock last; accuracy.md §8.2)
     - each statement has a timeout: a timer calls `connection.interrupt()`, since DuckDB has none of its own;
     - results are read chunk by chunk (`stream()` and `fetchChunk`) with running row and byte counts, and stopped at the cap, because they go back into the model's prompt;
     - a stopped or refused statement returns a typed tool error, which counts against the retry budget of 2;
     - `run_sql` lives in `evals/ablation`, never in `packages/agent/tools`;
     - a guard test fails if anything under `packages/` or `apps/` imports `evals/ablation`;
     - arm A's raw text never reaches an engine prompt or the engine's cache: arm A uses its own ModelClient with the cache off and its own call log, and a test checks the engine's cache directory is unchanged after a scripted arm-A run;
     - CI tests refuse, from a scripted arm B: `COPY … TO`, `read_csv('/…')`, `read_text('/etc/hostname')`, `read_blob`, `glob('/*')`, `INSTALL`, `LOAD httpfs`, `ATTACH`, `SET enable_external_access=true`, `SET lock_configuration=false`, `SET memory_limit=…`, a settings `PRAGMA` and `CREATE TABLE`;
     - a scripted runaway query (a cross join of `range()`) is stopped by the timeout with a typed error, and one that holds memory (a large `list()` or `string_agg`) fails with a typed out-of-memory error;
     - the spill cap is shown to work: a sort over the memory limit completes and leaves a spill file in the per-run temp directory, and the same sort on a test-only instance with a tiny `max_temp_directory_size` fails with a typed out-of-space error.
     The exception and its fence are recorded in STATE "Decisions made by agents".
   - **Measures (§4.5), each with a hand-computed test:**
     - numeric accuracy against the golden answers, via a deterministic parser for numbers in prose;
     - the unsupported-number rate. A number is supported when it matches, within tolerance, a value in the support set: the golden answers, arm C's fact table for the same job, or a value in the source cells. Numbers echoed from the question, dates and periods, ordinals and rank sizes ("top 10") are excluded. Source cells count only from the columns the question refers to (a `columns` field on each golden item, checked by the independent reviewer), since on a large table almost every small number appears somewhere. The rate is also reported without source cells. This set is wider than the spec's "data or golden set", which favours arms A and B (the conservative direction); accuracy.md says so;
     - driver accuracy, planted recall@5 and the distractor false-positive rate on smoke, by mapping each A/B answer to planted events with the same subject matcher as the scorer (metric, member, period and direction, parsed from the answer's structured fields: the arms are asked for a fixed JSON shape);
     - trap pass rate;
     - citation validity (for arm B, the SQL it ran, re-run and compared);
     - tokens and time.
   - **CI path:** FakeModel scripts for arms A and B on the smoke suite and the mini golden set.
7. **The held-out generated set:** new seeds and two archetypes the heuristics have never seen (§4.6), with planted events and answer keys like the 30.
   - A generator change, so new dataset hashes; the 30 are untouched.
   - **CI path:** generator tests, plus one held-out dataset in the offline baseline smoke.
8. **The baseline report.** Each run below, with its exact command. A run the free quota can't finish in a session is DEFERRED to the nightly runs with that command, as M14a's were.
   - **Golden v1, scripted:** `bun run eval -- --suite golden --model baseline`. Must run now (offline).
   - **Golden v1, a free model:** `bun run eval -- --suite golden` with the configured Groq routes. Likely DEFERRED (quota).
   - **Consistency on smoke:** `bun run eval -- --suite smoke --repeat 5` (configured model, cache off). Five times smoke on Groq's free planner quota needs several nights, so it's DEFERRED to the nightly.
   - **Ablation on smoke and golden v1:** `bun run eval:ablation -- --arms A,B,C --suite smoke` and `--suite golden`, scripted now and on a free model nightly. Each difference is reported per task, paired, with its 95% interval from the bootstrap (10,000 resamples, fixed seed). The scripted runs use canned FakeModel answers for arms A and B, so RESULTS.md labels them as harness checks, not an engine-vs-model comparison. RESULTS.md says "the engine adds accuracy" only where the 95% interval excludes 0 (§4.5).
   - Golden v1 here is the **dev split only**: held-out items are scored only in release runs (M21).
   - Results go in evals/RESULTS.md and STATE, gaps and DEFERRED runs listed with their commands. With the free-model runs deferred, the STATE row reads "DONE (code), real-model acceptance DEFERRED", as M14a's did.

The post-ship judge for citation precision, which EVALS §2 says is "planned for the golden set (M14)", is deferred to M21's release run and recorded under Known gaps: it needs a second judge model, so it belongs with the multi-model release run.

## Golden-set review (autonomy rule)

- **The plan:** the maintainer reviews about 40 items (§6.3), the answer SQL is written by a different session from the template code, and unreviewed items don't count toward the bars (§4.2).
- **Under the standing instruction:** the agent stands in for the maintainer, but the review must be independent of the author:
  - one session writes the items and their `answers.sql`;
  - a separate subagent, which has not seen `answers.sql`, re-derives each expected answer with its own query (or checks it against a published figure: EIA's published average prices, the article's tables). It also checks the wording, the tolerance and, for traps, the reason the data can't answer;
  - the review is recorded per item: `reviewed_by: "agent (autonomous mode)"`, `date`, `method` (independent SQL or published figure) and `agrees`.
  - An item counts toward the §4.7 bars only when the independent re-derivation agrees. When it disagrees, the item is fixed and reviewed again by a fresh subagent; one that still disagrees is replaced by a new item of the same kind and split, so the counts stay near 40, 8 and 12. Every golden result is labelled "agent-reviewed, not maintainer-reviewed" in RESULTS.md and STATE until the maintainer re-reviews.
- **Counts:** about 40 items over the four datasets, about 10 each; about 8 traps (20%) and about 12 held-out (30%), spread so each dataset has at least one of each.
- **Held-out honesty:** the held-out items live in `evals/golden/<dataset>/heldout.yaml`. A test fails if any file under `packages/` or `apps/` reads that path, and EVALS states the rule. A separate subagent writes them. Under autonomy, "never looked at while building" is only approximated (the writing session has seen them), and STATE records that.

## Risks

- **Quota:** the repeat and ablation runs on real models are large. They run over nights (#37), not in CI.
- **Downloads:** ScienceDirect's supplement is often bot-blocked, and EIA serves multi-row Excel headers and revises preliminary figures. The EIA fetch pins a dated final file, and a later revision is a new pinned version. A blocked host is DEFERRED, not worked around.
- **Arm A's cut:** on large datasets arm A sees a sample. The cut is stated in its input and beside its results, so the comparison stays fair and readable.
- **Leakage:** golden questions never reach the engine before its report is built, and the held-out file is guarded by a test.
