# Plan: M14 Measurement foundation

**Source:** docs/plans/analyst-grade.md §4 (accuracy program) and §5 "M14". Built under the autonomy rule (STATE, 2026-10-21): where the plan says the maintainer reviews something, the agent does it and records the choice in STATE.

**Goal:** every later milestone shows its effect in numbers. M14 builds the measuring tools and publishes today's engine on them, gaps included.

## Acceptance (from the plan)

- The scorer and the bootstrap have hand-computed tests.
- The whole harness runs offline with FakeModel in CI.
- A baseline report records today's engine on golden v1 (scripted and at least one free model), consistency over 5 runs on smoke, and the ablation on smoke and golden v1.
- The results are published as they are, gaps included.

## PRs, in order

1. **Golden-set format, scorer and bootstrap** (`evals/golden/`):
   - a Zod schema for golden items (question, kind: numeric / categorical / trap, expected answer, tolerance, the SQL that computes it, `reviewed_by`, `date`, `split`: dev / held-out);
   - the scorer: numeric within tolerance (read from the report's facts or an `aa ask` answer's facts), categorical exact, traps pass only on a refusal or caveat;
   - the paired bootstrap (10,000 resamples, fixed seed, 95% interval) as a pure function;
   - hand-computed tests for both. Spec: a new docs/specs/golden.md section, or EVALS.md §2 additions.
2. **Golden sets for the existing real datasets** (Online Retail II, NZ card spend): about 10 items each, answers from SQL written apart from the engine (`answers.sql`), checked by running that SQL on the derived files. Trap items about 20%. Held-out: 30% in a separate file, scored only in release runs.
3. **Two new real datasets** (§4.1a first wave): hotel bookings (the *Data in Brief* supplement, CC BY 4.0) and EIA-861M (public domain). Fetch scripts with licence checks and pinned checksums like `evals/real`, real-tier answer files, and about 10 golden items each. If a download is blocked from this machine, the fetch script and answers ship and the run is DEFERRED with the command.
4. **`aa eval --repeat N`:** consistency over N runs with the cache off; the five agreement measures of §4.3; disagreements written side by side.
5. **Ablation arms A and B** (`evals/ablation/`): arm A (files as text, truncated with a stated cut), arm B (DuckDB + one `run_sql` tool, no metric layer, no verifier), a deterministic number parser for prose answers, the same scoring; published prompts. Offline with FakeModel scripts in CI.
6. **Held-out generated set** (new seeds, two unseen archetypes) and **the multi-model matrix runner** (one command runs a suite across the configured model list, per-model results).
7. **Baseline report:** run everything offline (scripted baseline) and on the free models available; publish in evals/RESULTS.md and STATE, gaps and DEFERRED runs listed with commands.

## Decisions taken now (autonomy rule)

- **Golden-set review:** the plan has the maintainer review about 40 items. Under the standing instruction the agent reviews them: each item's answer is recomputed by its own SQL on the derived data in a test, and `reviewed_by` reads `agent (autonomous mode, 2026-10-22)`. The maintainer can re-review later; nothing else changes.
- **Real-model runs** that the free quota can't finish in a session are DEFERRED to the nightly runs with their exact commands, as M14a's were.

## Risks

- **Quota:** the ablation and repeat runs on real models are large; they run over nights (#37), not in CI.
- **Leakage:** golden questions never reach the engine before its report is built; the held-out file is not read while building.
- **Downloads:** the hotel supplement and EIA files are fetched from their publishers; a blocked host is DEFERRED, not worked around.
