# M10 plan: Doors

Acceptance (ROADMAP M10):
1. The same dataset gives an identical `report.json` (facts) via the CLI, the API and MCP.
2. Claude Desktop config from the docs works (DEFERRED if Claude Desktop or a model isn't available).
3. The Telegram bot works with long polling.

## Tasks, in order

1. **core: pause, confirm and render.**
   - `JobOptions.autoConfirm` (default true). When false, AWAIT_CONFIRM emits `awaiting_confirmation` and pauses (`StagePause`; `runJob` throws `JobError("AWAITING_CONFIRMATION")`), and confirmed metrics (stored in `job_meta`) resume it. Later stages read the confirmed definitions.
   - RENDER writes `report.html` with `renderReportHtml` (External badges already there).
   - INDEX_DOCS reports "loading the embedding model" progress (M9 gap).
2. **core: `JobManager`** (in-process queue, concurrency 1, ARCHITECTURE §6): create, status, events (history + live), metrics (YAML + plain words), confirm, report (json/html), ask, explain fact, delete, list. Every door goes through it.
3. **core: `askJob`.** The planner answers with claims (placeholders, fact ids, citations from the report). The claims are put into a synthetic finding of the verified report and run through `verifyReport`, so the answer follows the report's rules. Prompt `ask.md`.
4. **core: `explainFact`.** SQL, params, definition, input rows (re-found with the metric's row query) or the function and its inputs.
5. **apps/server.** Hono + zod-openapi: every endpoint in interfaces §1, SSE, `/openapi.json`, optional `API_TOKEN` bearer, CORS off, the viewer at `/`, MCP over streamable HTTP at `/mcp`.
6. **apps/mcp.** Tools `analyze_files`, `get_report`, `confirm_metrics`, `ask_report`, `explain_number`; resources `report://{job_id}`, `report-html://{job_id}`; stdio.
7. **apps/cli.** `aa analyze` (live stage view, interactive metric review, `--out`, `--open`), `aa ask`, `aa explain`, `aa serve`, `aa mcp`, `aa jobs ls|rm`, `aa eval` (pointer to M11). `aa run` stays.
8. **apps/telegram.** grammY with long polling, which calls the API client with `auto_confirm=true`, edits one status message, then replies with the summary and `report.html`.
9. **apps/viewer.** Vite + React: upload, live progress, metric confirmation, embedded report. Built into `dist/` and served by `aa serve`.
10. Docs: READMEs, the Claude Desktop config in the mcp README, the interfaces spec where it changes, and STATE.

## Tests

- **Core:** pause → confirm → resume; RENDER writes HTML; ask (claims verified, an invented fact dropped); explain (SQL fact rows).
- **Server:** every endpoint via `app.request`, SSE events, auth, OpenAPI.
- **MCP:** an in-memory client over tools and resources.
- **Telegram:** a fake Bot API transport (`bot.api.config.use`) plus `handleUpdate`.
- **Doors identity:** the coffee dataset with the scripted planner through the CLI, the API and MCP, with identical fact labels and values.

## Risks

- DuckDB holds a job file open while it runs, so ask/explain/metrics on a running job answer `409 JOB_BUSY`.
- The real model, Claude Desktop and a Telegram token are absent, so those checks are DEFERRED with commands.
- New dependencies: hono, @hono/zod-openapi, @hono/node-server, @modelcontextprotocol/sdk, grammy, vite, @vitejs/plugin-react (all MIT, free).
