# M3 plan: Workspace and profiling

Branch: `m3/workspace-profiling`. Human gate: `no`.
Sources: docs/ROADMAP.md M3, docs/ARCHITECTURE.md §3 (workspace tables), docs/specs/ingestion-and-profiling.md §5–8, AGENTS.md §4 (SQL in `.sql.ts`, parameterized).

## Data flow

`ingest()` (M2) → `normalizeTable()` per table (types, dates, numbers, currency, `_period`) → `store.loadJob()` writes `files`, `sources`, `t_<id>` (typed columns + `_row`, `_is_total`, `_period`) and the ingest issues → `profile()` runs SQL profiling, implausibility rules and entity matching over the workspace → `profile_columns`, `profile_tables`, `quality_issues`, `entities`, `entity_links`, plus a `profile.json` summary for metric drafting (M4).

## Tasks (in order)

1. **`packages/store`**
   - `openWorkspace(path | ":memory:")`, `close()`, `migrate()` (versioned migrations, `schema_migrations` table) creating every ARCHITECTURE §3 table. `chunks.embedding` is a variable-length `FLOAT[]`, because the dimension follows the embedding model.
   - A `sql` tagged template that emits `$n` placeholders plus params. Identifiers go through a checked `ident()` and are never concatenated from user input.
   - `query()`, `run()` and `appendRows()` helpers that use DuckDB's appender for bulk loads.
   - `loadJob(ws, ingest, normalized)` writes files, sources (one per table region and document section, with provenance), `t_<id>` and the mapped ingest issues.
2. **`packages/profile`, normalization (spec §6, test-first):**
   - `parseNumber` handles `1 234,56`, `1,234.56`, `1.234,56`, `(12)`, `12%`, currency symbols and codes, and decides the decimal separator per column by majority evidence.
   - `parseDate` handles ISO, `dd.mm.yyyy`, `dd/mm/yyyy`, `mm/dd/yyyy`, Excel serials, and EN/RU/UZ month names. dd/mm vs mm/dd is resolved per column by the majority test; still ambiguous → an assumption (day-first default); any ambiguity → a `date_format_ambiguity` issue.
   - Currency detection: mixed currencies are flagged, never converted.
   - Type inference: date, datetime, integer, decimal, currency, percent, boolean, category, id, text.
   - Snake-case column names with Cyrillic transliteration; the original header is kept as the label.
   - `_period` at the job grain (month by default; inferred from date coverage).
3. **Profiling, SQL in `.sql.ts`, hand-computed tests:**
   - Columns: null %, distinct, min/max, top 5 values, MAD outliers `|x − median| / (1.4826·MAD) > 5`.
   - Tables: row count, exact duplicates and duplicates on the inferred key, date coverage (first/last, missing periods).
4. **Implausibility rules → `quality_issues` with cell provenance:**
   - negative quantities in count-named columns;
   - rates above 100%;
   - future dates (with an injected `now`);
   - ×10/×100/×1000 jumps against the column median;
   - mixed currencies.
5. **Entity matching (spec §7):**
   - Candidate columns are found by name heuristics plus profile.
   - Normalization: lower-case, strip legal suffixes (LLC, OOO/ООО, MChJ, Ltd, …), drop punctuation, transliterate Cyrillic.
   - Matching: exact-normalized, or `jaro_winkler_similarity ≥ 0.92` in DuckDB plus a token-set overlap check.
   - Links below 0.97 confidence become assumptions.
6. **`profile.json` summary and a demo** (`bun run profile <paths…>` loads into a temp workspace and prints the profile).
7. Ledger, READMEs.

## Risks

- DuckDB type mapping for mixed or untyped columns: load normalized values with explicit types; columns that won't normalize load as VARCHAR.
- Over-eager implausibility rules on legitimately skewed data (wholesale vs retail amounts): the jump rule compares against the median of the same column and requires the ratio to sit near a power of ten. Tested on coffee Orders (no false positives).
